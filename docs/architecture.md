# DCATS — Architecture

SIH26247 · AI-Enabled Drone & Counter-Drone Threat Simulation Trainer.
Ships as an offline-first PWA and as a packaged Electron desktop app.

## Module map


## Data flow

Instructor Console → Scenario (catalogue, custom or procedural) → Simulation loop
(`requestAnimationFrame` → `tickSimulation` → `SwarmAI.updateThreatPosition`)
→ sensor visibility/latency model → operator actions (T/C/A/E)
→ AI advisory cue (ONNX or labelled fallback) → trainee classification choice
→ DecisionTree live scoring and mission-close outcome aggregation
→ endSimulation → AAREngine persist (IndexedDB) → AAR dashboard.

## AI model

- Snapshot RandomForest, 6 features `[speed, rcs, altitude, vx, vy, aggressive]`,
  300 trees, opset 17, trained on 12k synthetic tracks sampled from the
  simulation's own per-type envelopes (`src/store.js` speed ranges, RCS bases,
  altitude band) with ±2% sensor-jitter augmentation. Hold-out accuracy: 99.9%
  nominal, 99.8% under jitter — model ≈1.6 MB (`train_model.py`).
- Browser inference via `onnxruntime-web`. `vite.config.js` sets a build-time
  flag (`__HAS_ONNX_MODEL__`) so ONNX is only loaded when the model file exists;
  otherwise the tested heuristic fallback is used and labelled in the UI.
- The model is an advisory cue. The trainee explicitly accepts the cue or
  overrides it with a selected threat type; scoring uses the committed trainee
  answer and records the source in the AAR.

## Design system

Light, professional tool aesthetic: neutral page (#F2F4F7) with white cards,
1 px borders, navy accent (#1B4E8F), semantic status colours (threat red,
safe green, warn amber, violet), system font stacks with a monospace face for
data readouts, and SVG icons only. No gradients, glow, or emoji.

## Offline strategy

Service worker caches the app shell and the ONNX model (http/https only;
network-first navigations so rebuilds are picked up, cache-first hashed assets
and model); all state lives in Zustand + IndexedDB (`idb`, localStorage
fallback). The PWA is offline after its first online warm-up has cached the
hashed assets, runtime and model. The packaged Electron app serves its own
bundle over the internal `app://` scheme (no localhost server, no file:// fetch
limits), so it is offline by construction and runs the same ONNX inference.

## Resilience

- **View error boundary** (`src/components/ErrorBoundary.jsx`) wraps every route:
  a render crash shows a recoverable notice instead of a white screen, and
  navigating to another page resets it (boundary is keyed by route).
- **WebGL fallback**: if WebGL is unavailable (weak VM, RDP, old GPU) or the
  context is lost mid-session, the simulator automatically switches to the 2D
  Radar View, disables the 3D toggle and marks why — a mission can always run.
- **AI fallback**: absent model file → labelled built-in heuristic classifier.
- All three were verified with a forced-failure drill build (WebGL forced off,
  AAR forced to throw): fallback UI, boundary catch and navigation recovery all
  pass with zero console errors.

## Phase 2 — Unity (higher-fidelity VR target, planned)

The simulation core (scenarios, swarm AI, sensor model, scoring, AAR,
instructor tools) is deliberately renderer-agnostic. The shipped Three.js view
exposes a full-screen mode and an immersive WebXR look-around view (stereo
rendering + head tracking) when a compatible browser/headset is available; the
desktop console remains usable everywhere else. Phase 2 adds a Unity 6
deployment for physics-grade fidelity and controller-based VR training,
consuming the same scenario schema — the browser/Electron build remains the
unit-level deployment.
Full module mapping, proof-of-concept scope and effort estimates:
see `docs/unity_migration.md`.
